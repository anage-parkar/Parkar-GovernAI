AI Gateway

A centralized proxy for all LLM traffic in your organization — with built-in guardrails, cost tracking, prompt management, full audit logging, and MCP protocol support for AI agents.

EU AI Act Article 12 Human Oversight Audit Logging MCP Protocol Cost Governance

What is the AI Gateway?
The AI Gateway is a reverse proxy that sits between your applications and LLM providers (OpenAI, Anthropic, Azure OpenAI, etc.). Every LLM request flows through the Gateway, where it can be inspected, filtered by guardrails, logged for compliance, and cost-tracked. For organizations governed by EU AI Act Article 12 (record-keeping obligations), this provides the complete audit trail of every AI action.

💰

Spend Dashboard

Real-time LLM cost tracking across all providers and endpoints — with budget management, usage trends, and spend breakdowns by model and team.

/ai-gateway/spend-dashboard

The Spend Dashboard gives finance, procurement, and engineering leaders a live view of AI expenditure. Without centralized tracking, LLM costs are invisible until the monthly invoice arrives. The Gateway tracks every token, every request, every dollar — in real time.

Key Metrics Displayed

  • Total spend — across all endpoints and providers for the selected time period
  • Spend by endpoint — which proxy endpoints are consuming the most cost
  • Spend by model — cost breakdown per LLM model (GPT-4o, Claude 3.5, Llama, etc.)
  • Request volume trends — daily/weekly request counts and latency
  • Budget utilization — how much of the allocated budget has been consumed
  • Cost per request — average cost efficiency over time

Budget Management

Set budget thresholds per endpoint or organization-wide. When spend approaches the configured threshold, alerts are triggered — before the budget is exceeded, not after.

Cost governance: LLM costs can scale rapidly with usage. The Spend Dashboard provides the visibility needed to make informed decisions about which models to use, which endpoints to optimize, and where cost controls need to be applied.

Endpoints

Create and manage LLM proxy endpoints — configure the model, API keys, system prompts, rate limits, fallback endpoints, and response caching for each use case.

/ai-gateway/endpoints

An endpoint is a named proxy configuration that your applications call instead of calling an LLM provider directly. By routing through a Gateway endpoint, you gain: centralized key management, rate limiting, guardrail enforcement, full logging, and the ability to swap models without changing application code.

Creating an Endpoint

1
Name and descriptionGive the endpoint a clear name (e.g., "Customer Support Bot - GPT-4o") that identifies its purpose.
2
Select provider and modelChoose the LLM provider and specific model. The gateway handles the API call format differences between providers.
3
Configure API keySelect a provider API key from Settings → API Keys. The key is never exposed to calling applications.
4
Set system promptDefine the base system prompt for this endpoint — or leave empty for callers to provide their own.
5
Configure rate limitsSet requests-per-minute, tokens-per-minute, and per-user limits to prevent abuse and control costs.
6
Set fallback endpointConfigure a fallback endpoint to use when the primary is unavailable — ensures resilience.
7
Enable cachingToggle response caching to reduce costs and latency for repeated identical requests.

Endpoint Configuration Fields

FieldPurpose
ProviderOpenAI, Anthropic, Azure OpenAI, AWS Bedrock, Google, Cohere, etc.
ModelSpecific model within the provider
API KeyProvider key from Settings (never exposed to callers)
System PromptBase instruction prepended to every request through this endpoint
TemperatureDefault generation temperature (0.0–2.0)
Max TokensMaximum token limit per response
Rate Limit (RPM)Requests per minute cap
Rate Limit (TPM)Tokens per minute cap
Fallback EndpointBackup endpoint when primary is unavailable
Response CachingCache identical requests to reduce cost and latency
Prompt TemplateOptional template from the Prompts module
Active ToggleEnable or disable the endpoint without deleting it

Best practice: Create separate endpoints for different use cases (e.g., "Customer Support," "Internal Analytics," "Code Assistant") rather than a single generic endpoint. This allows per-use-case guardrails, rate limits, and cost tracking.

Playground

Interactive chat interface to test any configured endpoint — adjust parameters, observe responses, and track per-message cost before deploying to production.

/ai-gateway/playground

The Playground lets developers and compliance teams test endpoints directly from the browser. Before deploying an endpoint to production, test its system prompt, observe how guardrails affect responses, and verify cost per call against your budget targets.

Playground Features

  • Endpoint selector: Choose any configured Gateway endpoint to test against.
  • Chat interface: Full conversation interface with message history — just like the final user experience.
  • Temperature control: Adjust generation temperature in real time (0.0 = deterministic, 2.0 = very random).
  • Max tokens control: Set the maximum response length for this session.
  • Cost per message: See the token count and dollar cost for every request — immediately visible after each response.
  • Settings modal: Configure additional parameters specific to the selected endpoint.

Use Cases for the Playground

  • System prompt testing: Iterate on system prompts before production without touching application code.
  • Guardrail verification: Test that guardrails correctly block prohibited content or PII leakage.
  • Cost estimation: Estimate the cost of a typical user interaction before scaling up traffic.
  • Model comparison: Switch between endpoints pointing to different models to compare response quality.

All Playground requests are logged in the Logs module with a "playground" source tag — so you can distinguish test traffic from production traffic in your audit logs.

🛡️

Guardrails

Apply content safety, PII protection, prompt injection prevention, data leakage detection, and output quality filters to any endpoint — with a single toggle per rule.

/ai-gateway/guardrails

Guardrails are real-time filters that inspect every request and response flowing through a Gateway endpoint. They enforce your AI governance policies automatically — no application code changes required. A guardrail can block a request, redact content, log a violation, or alert on suspicious patterns.

Guardrail Categories

CategoryWhat It Protects AgainstExample Rules
PII ProtectionPersonal data leakage in inputs and outputsDetect and redact: SSNs, email addresses, credit card numbers, health data
Content SafetyHarmful, offensive, or inappropriate contentBlock: violent content, self-harm, adult content, hate speech
Prompt SecurityPrompt injection and jailbreak attemptsDetect: instruction override attempts, system prompt extraction, role manipulation
Data LeakageSensitive organizational data in responsesBlock: internal code snippets, confidential document content, API keys in outputs
Output QualityLow-quality or hallucinated responsesFlag: factual claims requiring verification, off-topic responses, incomplete outputs

Enabling Guardrails

  • Browse the Guardrail Catalog — all available rules with descriptions and risk categories.
  • Filter by category, severity, or search by name.
  • Toggle a guardrail ON to enable it for the selected endpoint — takes effect immediately.
  • Each guardrail shows an estimated impact on latency (most are < 5ms overhead).

Blocking vs. Logging: Some guardrails block requests entirely (e.g., prompt injection detection). Others log violations without blocking (e.g., output quality flags). Configure each guardrail's enforcement mode based on your risk tolerance.

Compliance Relevance

Guardrails provide technical enforcement of governance policies:

  • GDPR Article 25 (Privacy by Design): PII detection guardrails implement privacy-by-default at the API layer.
  • EU AI Act Article 9 (Risk Management): Content safety guardrails are technical risk mitigation measures that can be documented as controls.
  • EU AI Act Article 15 (Robustness): Prompt injection guardrails protect against adversarial attacks on the AI system.

Prompts

Create, version, and manage prompt templates for reuse across endpoints. Maintain your organization's approved prompt library with labels and search.

/ai-gateway/prompts

The Prompts module is the organization's approved prompt template library. Rather than every developer writing system prompts from scratch — or duplicating prompts across endpoints — prompts are created once, reviewed, versioned, and reused. This ensures consistency, enables governance oversight of what instructions are given to AI models, and provides an audit trail of prompt changes.

Prompt Fields

FieldDescription
NameA clear, searchable name (e.g., "Customer Support — Polite Response Style")
ContentThe prompt text itself — supports variable placeholders like {{user_name}}
DescriptionWhat this prompt does, when to use it, and any limitations
VersionSemantic version (v1.0, v1.1, v2.0) — each save can create a new version
LabelsCategorization tags (e.g., "customer-facing", "internal", "technical")

Versioning

Every time a prompt template is updated, a new version is created. Previous versions are preserved — you can see the full history of how a prompt evolved, and roll back to an earlier version if a change causes unexpected model behavior.

Linking to Endpoints

When creating or editing an endpoint, select a prompt template from the Prompts library. The template's content is applied as the default system prompt for that endpoint. When the template is updated and a new version is published, the endpoint can be updated to the new version — or remain pinned to a specific version for stability.

Governance use: The Prompts library provides governance teams with visibility into what instructions are being given to AI models. This is relevant for EU AI Act Article 13 (transparency) — you can document and justify every system prompt used in production.

Models

Browse the full AI model catalog, compare features across models, and estimate monthly costs before committing to a model for a production endpoint.

/ai-gateway/models

The Models page is a decision-support tool. Before selecting a model for a new endpoint, use this page to understand what each model supports, what it costs, and how it compares to alternatives. This informs better governance decisions — the right model for the right task at the right cost.

Three Tabs

Tab 1 — Model Catalog

  • Full list of available models across all configured providers
  • Filter by: provider, modality (text/vision/audio/image), supported features
  • Pagination for large catalogs
  • Each model card shows: provider, context window size, supported features, pricing (input/output per million tokens), and availability status

Tab 2 — Cost Calculator

  • Enter expected monthly request volume, average input tokens, and average output tokens
  • The calculator projects monthly cost across all models simultaneously
  • Compare the projected cost of GPT-4o vs. Claude 3.5 Sonnet vs. Llama 3.1 for your specific usage pattern
  • Useful for budget planning before adopting a new model

Tab 3 — Feature Comparison

  • Select up to 5 models for a side-by-side feature comparison
  • Compare: context window, fine-tuning support, function calling, vision support, streaming, JSON mode, tool use, max output tokens, knowledge cutoff
  • Export the comparison as a reference document

Governance link: Models selected and deployed through Gateway endpoints should be registered in the Governance section's Model Inventory. The Model Inventory is the compliance record — the Gateway Models page is the selection tool. Use both together.

Logs

Full request/response audit log for every LLM call through the Gateway — with auto-refresh, filtering, expandable details, and compliance-ready export.

/ai-gateway/logs

EU AI Act Article 12 (Record-keeping) requires that high-risk AI systems automatically log events for a defined period. The Logs module provides exactly this — every LLM request flowing through the Gateway is logged with full context, immutably stored, and available for compliance audits.

What Gets Logged

  • Timestamp — exact time of request (UTC)
  • Endpoint — which Gateway endpoint was called
  • Model — which LLM model processed the request
  • Status — success, blocked by guardrail, rate limited, error
  • Token counts — input tokens, output tokens, total tokens
  • Cost — dollar cost of this request
  • Source — which application or agent sent the request
  • Latency — response time in milliseconds
  • Guardrail flags — any guardrail violations detected

Log Table Features

  • Auto-refresh: The table refreshes every 10 seconds — live view of production traffic.
  • Search with debounce: Full-text search across log entries with intelligent debouncing (no request on every keystroke).
  • Filter by: Status (success/blocked/error), source application, endpoint, model, time range.
  • Expandable rows: Click any row to expand and see the full request prompt, response content, and metadata.
  • Pagination: Navigate through large log volumes efficiently.

Log Retention

Log retention period is configured in Settings. For EU AI Act compliance, the recommended minimum retention is 6 months for operational logs and 10 years for logs related to incidents or serious events.

Privacy consideration: Log entries may contain personal data from user inputs. Ensure your log retention and access policies are aligned with your GDPR data minimization obligations. The PII guardrail can be used to redact PII before logging.

Settings

Manage LLM provider API keys, configure organization-level Gateway preferences, and control global defaults for all endpoints.

/ai-gateway/settings

The Settings page is the configuration hub for the AI Gateway. Most importantly, it is where provider API keys are stored — securely, centrally, and separately from application code. Developers never need to handle provider keys directly.

LLM Provider API Keys

  • Add a key: Select the provider (OpenAI, Anthropic, AWS, Azure, Google, Cohere, etc.) and paste the API key. The key is encrypted at rest and never returned in plain text after saving.
  • Edit a key: Update a key without disrupting endpoints — the key reference (not the value) is stored in endpoints.
  • Delete a key: Removing a key disables all endpoints that reference it. Review impacted endpoints before deleting.
  • Multiple keys per provider: Maintain separate keys for production and staging environments, or for different cost centers.

Organization Settings

  • Default rate limits — organization-wide defaults applied to all new endpoints unless overridden
  • Log retention period — how long request logs are stored
  • Budget alerts — thresholds for spend notifications
  • Default guardrails — guardrails automatically applied to all new endpoints

Key security: API keys are stored encrypted and never exposed through the API after initial creation. Only the key name/label is visible after saving. This means if the Settings page is accessed by an unauthorized user, they cannot retrieve provider keys.

MCP Gateway

The Model Context Protocol (MCP) Gateway governs AI agents that use tools to interact with external systems. It provides authentication, tool access control, audit logging, and human approval workflows for agentic AI operations.

What is MCP?
The Model Context Protocol (MCP) is an open standard that allows AI models to call external tools — databases, APIs, code execution, file systems, and more. The MCP Gateway controls which agents can use which tools, under what conditions, with what approvals. Without a governed MCP Gateway, AI agents can take uncontrolled actions in your systems.

🔑

MCP — Agent Keys

Issue and manage authentication keys for AI agents connecting to the MCP Gateway. Control which agents are authorized to use tools.

/ai-gateway/mcp/agent-keys

Agent Keys are the authentication credentials that AI agents use to connect to the MCP Gateway. Only agents with a valid, active key can access MCP tools. This is the identity gate — the first line of defense against unauthorized AI agent activity.

Managing Agent Keys

  • Issue a key: Create a named key associated with a specific agent or application. Set an optional expiry date and scope restrictions.
  • Revoke a key: Instantly revoke a key to disconnect an agent from all MCP tools — useful when an agent is decommissioned or compromised.
  • Scope restrictions: Limit a key to specific tool categories (e.g., "this agent can only access database read tools, not write tools").
  • Expiry management: Keys with expiry dates automatically become invalid after the expiry — reducing the risk from forgotten or abandoned keys.

Governance principle: Every AI agent connecting to MCP tools should have its own unique agent key — never share keys between agents. This enables per-agent audit trails and granular revocation without impacting other agents.

🖥️

MCP — Servers

Register and configure MCP servers that expose tools to AI agents. Manage server health, connection settings, and tool availability.

/ai-gateway/mcp/servers

An MCP Server is a service that exposes a set of tools that AI agents can call. For example, a database MCP server exposes tools like query_database and list_tables. The MCP Gateway acts as the broker between agents (who hold Agent Keys) and these servers (which expose tools).

Server Configuration

  • Server name and URL: A unique name and the connection endpoint for the MCP server.
  • Authentication: Configure how the Gateway authenticates to the MCP server (API key, OAuth, mTLS).
  • Tool discovery: The Gateway automatically discovers tools exposed by the server and populates the Tool Catalog.
  • Health monitoring: Connection status and uptime are monitored continuously — unhealthy servers are flagged.
  • Enabled / Disabled toggle: Disable a server to prevent any agent from using its tools without deleting the configuration.

Example MCP Servers: Database query server, file system server, web search server, code execution server, GitHub integration server, Slack messaging server, internal REST API wrapper.

🔧

MCP — Tools

Browse the complete catalog of tools available to AI agents through the MCP Gateway — understand capabilities, parameters, and access restrictions.

/ai-gateway/mcp/tools

The Tool Catalog is automatically populated by the Gateway when MCP servers are connected. It provides a browsable inventory of every action AI agents can take through the Gateway.

Tool Catalog Features

  • Full tool inventory: Every tool exposed by registered MCP servers, with name, description, input parameters, and output schema.
  • Access control: See which agent key scopes can access each tool — and configure restrictions.
  • Risk classification: Tools are classified by risk level based on their capabilities (read-only vs. write, reversible vs. irreversible).
  • Usage statistics: How often each tool is called, by which agents, and the success/failure rate.

MCP — Audit Log

Complete, immutable audit trail of every MCP operation — which agent used which tool, with what parameters, and what the result was.

/ai-gateway/mcp/audit-log

The MCP Audit Log is the compliance record for all AI agent actions. EU AI Act Article 12 (record-keeping) and Article 14 (human oversight) both require that AI system actions can be traced, reviewed, and investigated. The Audit Log provides exactly this trail for every tool call made through the MCP Gateway.

What Is Recorded

  • Agent identity — which agent key was used (maps back to a specific agent)
  • Tool called — which MCP tool was invoked
  • Parameters — the exact input parameters passed to the tool
  • Result — the tool's response (or error)
  • Timestamp — exact time of execution (UTC)
  • Approval status — whether this call required approval and who approved it
  • Guardrail checks — any guardrail rules that were evaluated

Filtering and Investigation

  • Filter by: agent, tool, server, time range, approval status, result status
  • Search across parameter content — find all calls that touched a specific resource
  • Export filtered results for incident investigation or regulatory submission

Governance value: When an AI agent takes an unexpected action — deleting data, sending a message to the wrong recipient, executing unauthorized code — the Audit Log provides the complete forensic record needed to investigate what happened, why, and who authorized it.

✔️

MCP — Approvals

Human-in-the-loop approval workflow for sensitive AI agent actions — require explicit sign-off before high-risk tool calls execute.

/ai-gateway/mcp/approvals

EU AI Act Article 14 requires human oversight measures for high-risk AI systems — meaning humans must be able to intervene when necessary. The Approvals module implements this at the tool-call level: for any tool classified as high-risk or irreversible, an AI agent's request is held in a queue until a human reviewer approves or rejects it.

The Approval Workflow

1
Agent requests a high-risk tool callThe agent sends a tool call request to the Gateway. The Gateway identifies it as requiring approval based on the tool's risk classification.
2
Request queued in ApprovalsThe tool call is placed in the approval queue with the full context: agent ID, tool name, parameters, and timestamp. The agent waits.
3
Human reviewer approves or rejectsA designated reviewer sees the request in the Approvals dashboard. They can review the parameters, understand the intended action, and approve or reject with a comment.
4
Gateway executes (or blocks) the callIf approved, the Gateway forwards the tool call to the MCP server. If rejected, the agent receives a rejection response. All outcomes are logged in the Audit Log.

Approval Queue Columns

  • Agent — which agent is requesting the action
  • Tool — which tool is being called
  • Parameters — the exact parameters (expandable)
  • Requested at — timestamp of the request
  • Waiting time — how long the agent has been waiting
  • Actions — Approve or Reject buttons

Auto-approve rules: Configure auto-approval for low-risk tools from trusted agents, so only genuinely sensitive operations require human review. This keeps the approval queue manageable without compromising oversight of high-risk actions.

MCP — Guardrails

Apply real-time input/output guardrail rules specifically to MCP tool calls — prevent data leakage, enforce policy compliance, and protect external systems from AI agent misuse.

/ai-gateway/mcp/guardrails

MCP Guardrails work the same way as Gateway Guardrails — but they are applied specifically to tool call inputs and outputs, rather than LLM chat messages. They protect against AI agents inadvertently (or maliciously) sending sensitive data to external tools, or receiving dangerous content back from tools.

MCP-Specific Guardrail Rules

RuleWhat It Prevents
PII in tool inputsAI agent passing personal data to external APIs without authorization
Credential detectionAgent passing API keys, passwords, or tokens as tool parameters
Data exfiltrationAgent sending large data volumes to external endpoints (potential data leak)
SQL injection in queriesMalicious SQL payloads in database query tool parameters
Tool output sanitizationDangerous content in tool responses that could influence subsequent agent actions
Rate limiting per toolAgent calling a tool at an abnormal rate (potential runaway agent)

Why this matters: AI agents are increasingly capable of taking sequences of actions autonomously. A single guardrail failure — an agent passing PII to a third-party web search API, for example — can create a GDPR violation, a security incident, and a regulatory disclosure obligation simultaneously. MCP Guardrails are the last line of defense before an agent's action reaches an external system.

Linking to Governance Policies

Each active MCP guardrail can be linked to a policy in the Governance section's Policy Manager. This creates the traceability chain auditors expect:

  • "We have a PII Handling Policy" (Policy Manager)
  • "The policy requires that PII is never sent to unapproved external services" (Policy content)
  • "This is enforced by the PII Detection MCP guardrail applied to all database and web tools" (MCP Guardrails)
  • "The guardrail has blocked 14 PII leakage attempts in the last 30 days" (Audit Log)
